# R9 UI 2.0 屏幕点亮与调试记录

记录日期：2026-11-21。对象为「ESP32S3 功能板 TFT版」验证板。本文按发现顺序记录问题、误判与最终结论，供后续复现时少走弯路。

## 一、验证板硬件参数

| 项目 | 参数 |
| --- | --- |
| MCU | ESP32-S3-WROOM-1-N16R8（16 MB Flash / 8 MB OPI PSRAM） |
| MAC | `64:E8:33:7F:4D:B4` |
| 串口 | CH340K，COM4，115200 |
| 屏幕 | 1.8 英寸 128×160 ST7735S，8 脚 SPI，横屏安装后可视区 160×128 |
| 屏幕连接 | FPC 排线压接，不是排针排母 |
| 按键 | 6 个轻触键 IO13–IO18，另有 BOOT 键 IO0 可补第 7 键 |
| 温湿度 | DHT11，DATA 接 IO8 |
| 模拟量 | 无 MQ-2 / MQ-135；IO1 为光敏电阻 |
| 板载 | 4 个 LED（IO4–IO7）、WS2812（IO48）、蜂鸣器（IO47）、继电器（IO2） |

| --- | --- | --- |

## 二、踩过的坑

### 坑 1：从 PDF 文本流推断引脚，顺序全反

用 PDF 文本提取拿到的引脚序列是按阅读顺序输出的，与原理图上的连线和引脚编号没有对应关系。据此得出 `SCL=IO9, SDA=IO10, RES=IO11, DC=IO12, CS=IO21, BLK=IO38`，与真实接法几乎完全错位。

**教训**：原理图必须渲染成图片按图读线，不能依赖文本提取的结果做电气判断。

### 坑 2：把屏幕规格误判为 240×320

早期按「高分辨率全彩」的预期设计了 240×320 版式，实际面板是 128×160。整套版式需要按 160×128 重做，字号、行数、信息密度全部改变。

**教训**：动手排版之前先确认物理分辨率，宁可先做一次纯色填充验证。

### 坑 3：背光不亮被当成「屏幕没供电」

第一块板背光完全不亮，据此判断模块无供电。换板后背光正常，说明第一块板确有问题，但当时无法区分「模块坏」与「接线错」，在两块板之间反复试错浪费了大量时间。

**可复用的判据**：ST7735 模块的背光 LED 经限流电阻直接接 VCC，没有使能脚。只要模块有 3.3 V，背光必然发亮，任何固件都关不掉。**背光不亮 = 模块没电**，可以直接跳到硬件检查，不必再试驱动。

### 坑 4：SPI 重复 `begin()` 不切换引脚，制造了「多组都能工作」的假象

这是最误导人的一个。扫描固件逐组调用 `SPI.begin(scl, -1, sda, -1)`，看起来每组都重新配置了引脚。实际上连续调用时引脚映射并未真正切换，屏幕上出现的多种颜色**始终是用第一次配置的那组引脚画出来的**。

由此产生了两个错误结论：

1. 「交换 SCL/SDA 也能工作」——不可能，是假象。
2. 「引脚是 21/38」——实际是第一次配置的 38/21。

**破解方式**：写一个只初始化一次、只换颜色的固件。单次初始化下能正常出红绿蓝，才说明这组引脚成立。

**教训**：ESP32 的 `SPI.begin()` 不要重复调用。需要切换引脚时，先 `end()`，或用独立的 `SPIClass` 实例，或干脆每次上电只配置一次。

### 坑 5：为「提高稳定性」降频，反而破坏了时序

看到画面闪烁，把 SPI 从 20 MHz 降到 8 MHz、再降到 1 MHz，结果完全不出图。真正原因是引脚接错，降频只是让错误更难被发现。

**教训**：闪烁优先怀疑接触与引脚，不要先动频率。频率应作为独立变量单独验证。

### 坑 6：拿另一块板的示例代码套用

《点菜代码》用的是 `CS=15, RST=21, DC=2, SCK=14, MOSI=13`，那是另一块 ESP32 点菜器的接法，与这块 S3 功能板无关。盲目套用等于多试了一组无效组合。

**教训**：示例代码只在确认是同一块板时才有参考价值。屏幕型号相同不代表引脚相同。

### 坑 7：小字号行高超过容器高度，底栏被裁

`FontCN` 对 12 px 以下的字号统一返回 14 px 行高，而底栏高度只有 13 px。排版按 `(容器高 - 行高) / 2` 居中，结果文字被裁掉下半截。

**修复**：底栏改用固定基线偏移，不再按行高居中。

### 坑 8：配网页行距按大屏计算，内容溢出屏幕

按 240×320 的行距排 5 行内容，在 128 高度的屏上溢出约 28 px，最后一行「浏览器打开」被底栏盖住。

**修复**：压缩为 5 行、行距 17 px，把地址与 MAC 合并到底部。

### 坑 9：标签与数值的横向偏移不足，文字重叠

「连接热点」四个汉字占 48 px，而数值起点只偏移 40 px，两者叠在一起。**修复**：偏移改为 54 px。

### 坑 10：按键 IO 顺序与丝印排列不一致，方向键整体错位

板子中部的四个方向键看着是「上左下右」一横排，丝印也按这个顺序印 `IO15 IO16 IO18 IO13`，但实测按下后串口报的事件是：

```
按"上" → IO17    按"左" → IO15
按"下" → IO18    按"右" → IO16
```

方向键四个 IO 与丝印顺序对不上，按原先「按丝印从左到右推」的映射，上下键实际触发的是左右键，表现为「按了有反应但方向不对」，或者干脆被页面忽略。

**教训**：按键映射只能实测，不能看丝印、不能看原理图编号顺序。做法是烧一个只做扫描的固件——把所有候选 IO 设成 `INPUT_PULLUP`，逐个按下去，看哪个 IO 变低。事件要写进环形缓冲并每 5 秒重播一次，否则串口没打开时事件全丢。

### 坑 11：`view` 与 `phase` 两套状态并存，渲染条件要求两者同时成立

答题状态机里 `phase`（Menu/Story/Question/Judge/Finished）和界面 `view`（Menu/Question/Sensor/…）是两套独立变量。按下 OK 开始考试时，代码只把 `phase` 推到题目，`view` 仍停在 `Menu`；而渲染分支写的是：

```cpp
if (view == View::Question && session.phase == exam::Phase::Question)
```

两个条件同时成立才画题目，于是 `phase` 早已是题目、屏幕却一动不动，**看起来完全像按键失灵**。按键处理其实一直在正常执行。

**修复**：渲染以 `phase` 为准，`view` 只作为「用户手动切到别的页面」的覆盖：

```cpp
if (session.phase == exam::Phase::Question &&
    (view == View::Menu || view == View::Question))
```

**教训**：只要有两套状态描述同一件事，就一定会不一致。排查「按键没反应」时，第一步不是怀疑按键，而是把 `phase`、`view`、`busy` 三个值打到串口——这次日志显示 `phase=2 busy=0 ready=1`，立刻排除了按键和网络。

### 坑 12：`WiFi.begin()` 放在自建 FreeRTOS 任务里会静默失败

网络层把 Wi-Fi 连接写进了自建的 `exam-network` 任务，结果一直是：

```
wifi=6  ip=0.0.0.0  rssi=0
```

状态码 6 是 `WL_DISCONNECTED`，没有任何报错。同一份凭据在 `setup()` 里直接 `WiFi.begin()` 两秒就能拿到 IP。

**修复**：`WiFi.begin()` 移回主任务（`begin()` 里），自建任务只负责 MQTT 循环。

**教训**：ESP32 的 Wi-Fi 协议栈初始化对调用上下文敏感。凡是「凭据确定正确、扫描能看到热点、但状态一直是 6」的情况，先把 `WiFi.begin()` 移到 `setup()` 里做最小验证，再谈任务架构。

### 坑 13：配网页密码只输进了 6 位，表现却是「连不上」

屏幕上配置页的密码框只显示 6 个点，实际密码是 8 位。设备反复重连失败，日志只有 `wifi=6`，看不出是密码问题——因为 Wi-Fi 密码错误和设备不在范围内，在 ESP32 侧是同一个状态码。

**排查捷径**：不要反复在配网页上试，直接烧一个固件把正确配置写进 NVS（`Preferences`，命名空间 `zlc-config`，键 `ssid/wifi/group/mqpass/name/host/port`），再烧回正式固件。既排除了输入错误，也省掉每次手机配网。

**教训**：`wifi=6` 不区分「密码错」「不在范围」「AP 拒绝」，必须用已知正确的凭据直连一次做对照。

### 坑 14：MQTT Client ID 用了自定义格式，与课程规范不符

原先用 `zlc-<组号>-<MAC>` 作 Client ID，能连上也能收发，但课程《任务 A》的连接参数表规定：

```
客户端 ID   esp32-<组号>（必须唯一，如 esp32-24001）
```

A1 有一条 2.5 分是「订阅/发布主题正确、Client ID 唯一」，自定义格式属于不符规范。已改为 `esp32-<组号>`。组号本身唯一，所以 ID 天然唯一。

**教训**：能连通 ≠ 符合规范。评分表里写死的字符串格式（主题、Client ID、字段名）要逐字对照，不要「意思对了就行」。

## 三、可复用的排查方法

1. **单变量对照**：每次只改一个因素（引脚、频率、初始化表），并保留上一次能工作的版本做对照。
2. **静帧测试**：只画一次、不再刷新，用于区分「通信不稳」与「刷新逻辑有问题」。
3. **硬件 SPI 与软件时序各测一次**：软件时序完全绕开 SPI 外设，若不工作则问题在硬件层。
4. **复位白闪是正常现象**：每次重新初始化屏幕会短暂变白，不是故障。
5. **背光判据**：背光不亮直接查供电，不要试驱动。
6. **一次只初始化一次 SPI**：这条能避免一大类假象。
7. **按键只能实测**：扫描固件 + 环形缓冲重播，逐键确认 IO，不看丝印、不看原理图编号顺序。
8. **「按键没反应」先打状态**：把 `phase / view / busy` 三个值打到串口，能立刻区分「按键没到」和「画面没刷」。
9. **三处同时看**：设备串口状态日志、broker 的 `New client connected` 日志、服务进程日志（收没收到上行）。只看一处会误判——设备显示「在线」但服务器没收到消息，问题就在主题或 Client ID。
10. **最小联网固件隔离架构问题**：先写一个只在 `setup()` 里连 Wi-Fi + MQTT + 发一条 hello 的固件，通了再回到正式工程。这次正是靠它把问题锁定在「`WiFi.begin()` 的任务上下文」。

## 五、联网与答题链路实测

这一节记录的是在验证板上跑通、而不是从文档抄来的东西。

### 5.1 接入参数

| 参数 | 值 |
| --- | --- |
| 服务器 | `124.70.71.221:1883` |
| 上行 / 下行 | `/iot/game/<组号>/up` · `/iot/game/<组号>/down` |
| Client ID | `esp32-<组号>` |
| 用户名 | 组号 |
| 密码 | 组号 + MAC 经算法算出的 8 位十六进制 |

### 5.2 密码算法（固件内实现）

```text
1. MAC 去冒号 → 12 位 hex（大小写不敏感）
2. SUM   = 组号(十进制) + 2026
3. 12 位串每 4 位一组转十进制 → M1 M2 M3
4. TOTAL = SUM + M1 + M2 + M3
5. 密码  = TOTAL % 2^24，转 8 位 hex，不足补 0
```

验算：组号 99002、MAC `64:E8:33:7F:4D:B4` → `101028 + 25832 + 13183 + 19892 = 159935 = 0x270BF` → `000270bf`，与服务器 `gen_pass.py` 输出一致。

### 5.3 协议 2 的强制字段

服务器对协议 2 的设备有一组硬校验，缺一项就返回 `error` 并且**不改状态**：

| 字段 | 要求 |
| --- | --- |
| `protocol` | 必须为 `2`，否则走旧的单向流程 |
| `request_id` | `[A-Za-z0-9_-]{1,80}`，同一条请求重发必须用同一个 id（服务器按 id 做幂等回执） |
| `exam_id` | 必须与首次 `resume_ack` 返回的一致，否则 `409 考试会话已改变` |
| `revision` | 必须等于服务器当前 revision，否则 `409 请求进度已过期` |

因此「重试」在本协议里不是重发一条新请求，而是**先 resume 拿快照再继续**。固件里对应 `fail()` 只置 `resumeWanted_`，绝不清空后重发答案。

### 5.4 报文类型的实际情况

课程文档列了五类：`story / question / judge / level_result / game_over`。实测服务器（`game-engine.js`）在协议 2 下只发四类：

```
story  question  judge  game_over
```

`level_result` 在当前服务端代码里**没有生成路径**，只在 `simulate_dev.js` 和旧备份的注释里出现。协议 2 用 `judge → continue → current(p)` 代替了「先结算再进下一关」的两段式，关卡切换直接下发下一关的 `story`。

固件仍保留 `level_result` 的解析分支（v1 路径），防止旧数据或教师改版时把状态机打崩，但主流程按四类走。

### 5.5 答题推进顺序

```
hello  → hello_ack   （data.protocol=2 才升级为协议 2）
resume → resume_ack  （拿到 exam_id / revision / phase / current）
start  → story       （剧情第 1 页）
story_next → story … → question
answer → judge       （判题：correct / correct_answer / hp / explain）
continue → 下一题 question，或下一关 story，或 game_over
```

`advance()` 在 `!ready || busy()` 时会静默返回空串，所以「按了没反应」在协议层是合法行为——这也是坑 11 容易误判的原因。
