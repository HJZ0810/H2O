# 踩坑与经验总结 · v1

> 独立文档，不依附任何代码版本。记录 2026-11-19 ~ 2026-11-21 两天里在
> ESP32-S3 + ST7735 + OneNET + 自建 MQTT 服务器 上实际踩过的坑。
> 每条按「现象 → 根因 → 怎么确认 → 怎么修」写，重点在**怎么确认**，
> 因为排查方法比结论更容易复用。

---

## 一、显示与硬件

### 1. ST7735 只允许初始化一次

- **现象**：改引脚后重新 `tft.init()`，画面仍按旧引脚输出，怎么改都无效。
- **根因**：SPI 总线 `SPI.begin(sclk, miso, mosi, ss)` 在本核只生效一次，第二次调用被忽略。
- **确认**：在 `begin()` 前后打印实际引脚配置，发现仍是第一次的值。
- **修法**：引脚只在最外层初始化一次；换引脚必须重启，不能在运行期切换。
- **教训**：屏幕不亮/花屏，先怀疑「初始化顺序」，再怀疑接线。

### 2. 按键 IO 与丝印顺序不一致

- **现象**：方向键按「上」光标往左走。
- **根因**：厂商板四向键的 IO 顺序与丝印排列无关，必须实测。
- **确认**：逐个按键打印 `digitalRead` 的 IO 号，建一张「物理位置 → IO」表。
- **修法**：实测结果写进 `Board.h`：上=IO17 左=IO15 下=IO18 右=IO16 OK=IO13 返回=IO14。
- **教训**：不要信丝印，也不要信「应该是顺序排的」。

### 3. 状态机有两个「当前页面」变量

- **现象**：按键偶尔完全失灵，重启就好。
- **根因**：`view` 与 `phase` 两个变量都能决定当前页面，某条路径下两者不一致，
  渲染按 A 走、按键分发按 B 走，就表现为「按了没反应」。
- **确认**：按键事件里同时打印 `phase` 和 `view`，抓到不一致的那一次。
- **修法**：只保留一个状态源，另一个改为派生量。
- **教训**：凡是「有时好有时坏」的输入问题，先查状态是否被两处同时维护。

### 4. USB 供电不稳导致的假故障

- **现象**：串口日志每次都在同一行之后断掉，看起来像程序崩在那一行。
- **根因**：USB 线接触不良，供电跌落导致整机复位，日志自然停在随机位置。
- **确认**：看复位原因——`rst:0x1 (POWERON)` 是整机断电重启，
  `rst:0xc (RTC_SW_CPU_RST)` / panic handler 才是软件崩溃。前者与代码无关。
- **修法**：换线换口；把关键日志改成纯 ASCII 以便在断流时也能读。
- **教训**：日志「总在同一处断」是伪规律，先看复位原因再改代码。

## 二、网络与鉴权

### 5. `WiFi.begin()` 放进自建任务会静默失败

- **现象**：网络任务跑起来了，但永远连不上，也没有错误码。
- **根因**：ESP32 Arduino 核的 Wi-Fi 协议栈要求初始化在主任务上下文，自建任务里调用不报错但不生效。
- **确认**：把 `WiFi.begin()` 挪回 `setup()`，同一份代码立刻连上。
- **修法**：`setup()` 里完成 `WiFi.begin` + 等待连接，业务逻辑再放进任务。
- **教训**：底层的「无返回值的初始化」最坑，失败时不报错，只能靠二分定位。

### 6. `WiFi.macAddress()` 在 Wi-Fi 初始化前返回全 0

- **现象**：按 MAC 算出的密码与服务器端算出的对不上。
- **根因**：`WiFi.macAddress()` 依赖 Wi-Fi 驱动已启动；未启动时返回 `00:00:00:00:00:00`，
  参与哈希后结果完全不同。
- **确认**：把读到的 MAC 打印出来，是 12 个 0 就中了。
- **修法**：改用 `esp_read_mac(mac, ESP_MAC_WIFI_STA)` 从 eFuse 直读，与 Wi-Fi 状态无关。
- **教训**：凡是要参与运算的硬件标识，都用底层接口读，别用封装过的便捷函数。

### 7. MQTT Client ID 必须符合服务器规范

- **现象**：连接被拒，服务器日志显示 ID 格式不符。
- **根因**：自定义成 `zlc-99002-64E8337F4DB4`，而规范要求 `esp32-<组号>`。
- **确认**：看服务端日志里的 `New client connected ... as <id>`，与规范逐字符比对。
- **修法**：改为 `esp32-240401`。
- **教训**：Client ID 是协议的一部分，不是备注，必须按文档逐字对照。

### 8. 密码必须由代码算，不能手填

- **现象**：手填密码在测试环境能过，换块板子就失败。
- **根因**：密码与硬件 MAC 绑定，换板子 MAC 变，密码必须重算。
- **修法**：固件内按「组号 + MAC」派生，与服务器 `gen_pass.py` 对齐；
  实测 `240401` → `00049916`，两边一致。
- **教训**：凡是「与设备身份绑定」的凭据，一律运行时派生，禁止落配置。

### 9. OneNET：密码不是设备密钥，而是用密钥算出的 token

- **现象**：clientId = 设备名、username = 产品 ID、password = 设备密钥，
  服务器一律回 `CONNACK 4`（用户名或密码错误）。
- **根因**：OneNET 安全鉴权要求的是 token，密钥只是签名的 HMAC key。
- **确认**：手写一个只发 CONNECT 的最小客户端，打印 CONNACK 返回码，
  能在 PC 上稳定复现，就排除了固件问题。
- **修法**：
  ```
  resource           = products/{pid}/devices/{dev}
  stringForSignature = et + "\n" + method + "\n" + resource + "\n" + "2018-10-31"
  sign               = base64( HMAC-SHA1( base64decode(key), stringForSignature ) )
  password           = version=2018-10-31&res=...&et=...&method=sha1&sign=...
  ```
- **教训**：遇到 `4` 不要急着重填凭据，先用最小客户端把「平台拒绝」和「网络不通」分开。

### 10. token 里的 `et` 是绝对时间，必须先对时

- **现象**：token 算法完全正确，但仍然 `CONNACK 4`。
- **根因**：`et = 当前时间 + 有效期`。设备时钟停在 1970 年，算出的过期时间在过去。
- **确认**：串口打印 `time(nullptr)`，小于 17 亿就是没对时。
- **修法**：连上 Wi-Fi 后 `configTime()` + 轮询等时间就绪，再算 token；
  固件里做硬门禁——时间未就绪就不发连接。
- **教训**：任何带时间戳的签名，都要先确认时钟，否则会误判成密钥错。

### 11. `state=4` 不是超时

- **现象**：日志写 `connect FAIL state=4`，我一开始当成连接超时去查网络。
- **根因**：PubSubClient 在收到 CONNACK 时把返回码原样放进 `state()`，
  `4` 是协议层的「用户名或密码错误」，不是 `-4`（超时）。
- **确认**：对照库的返回值定义：负数才是本地网络错误，0~5 是服务端 CONNACK。
- **教训**：负数和正数含义相反，看日志要带符号。

## 三、平台操作

### 12. 产品建不出来，报 `Uid Required`

- **现象**：创建产品向导填完点确定没反应，顶部飘过 `Uid Required - Uid Cannot be empty`。
- **根因**：账号未实名认证，部分接口取不到 uid。
- **修法**：完成个人实名认证后恢复正常。
- **教训**：平台侧「点了没反应」优先看网络面板/顶部提示，别怀疑自己填错。

### 13. 资源空间不对，产品列表是空的

- **现象**：同一账号，已打开的页面能看到产品，新开标签打开列表是「暂无数据」。
- **根因**：开通新服务后控制台切到了另一个资源空间；且列表接口依赖页面内会话状态，
  整页重载会丢。
- **确认**：点右上角「我的空间」看当前空间，再对比设备总数。
- **修法**：在当前空间里重建产品与设备。
- **教训**：控制台里「数据凭空消失」，先查资源空间，再查筛选条件。

### 14. 物模型标识符必须与固件完全一致

- **现象**：设备在线、上报返回 ok，但属性页全是 `undefined`。
- **根因**：品类自带模板的标识符是 `temp_value` / `humidity_value`，
  固件发的是 `temperature` / `humidity`，平台按标识符丢弃。
- **修法**：导入自定义物模型 JSON，标识符与固件一一对应；导入后必须点「保存」才生效。
- **教训**：`publish` 成功只代表报文发出去了，不代表平台收了；要去看属性页或回执 topic。

## 四、工具链

### 15. Arduino 预处理器把函数原型插到结构体前面

- **现象**：`'Sample' does not name a type`，而结构体明明定义在函数之前。
- **根因**：.ino 会被自动生成函数原型并插到文件最前面，此时结构体还没定义。
- **修法**：把结构体/别名放进头文件，或在签名里写全限定名（`bmon::Sample`）。
- **教训**：.ino 里「明明定义了却说不认识」，先想到自动插原型。

### 16. ESP32 core 3.x 移除了 `ledcSetup` / `ledcAttachPin`

- **现象**：编译报 `ledcSetup was not declared`。
- **修法**：改成按引脚的 `ledcAttach(pin, freq, resolutionBits)` + `ledcWrite(pin, duty)`。
- **教训**：换核大版本先查外设 API 变更表，别照抄旧教程。

### 17. 串口中文在这台机器上是乱码

- **现象**：串口助手显示 `??????`。
- **根因**：固件输出 UTF-8，终端按 GBK 解释。
- **修法**：调试日志一律纯 ASCII；中文只出现在界面和文档里。
- **教训**：调试通道的编码要固定，否则关键信息会被自己弄丢。

### 18. Shell 管道把反斜杠吃掉

- **现象**：用 Python 脚本批量改代码，写进文件的 `"\n"` 变成了真实换行，编译报字符串未闭合。
- **根因**：多层引号 + heredoc 叠加，反斜杠被某一层解释掉了。
- **修法**：含转义的代码不再用脚本拼接，直接写文件；或把 `\n` 换成拼接表达式。
- **教训**：代码生成只用于机械替换，涉及转义的段落宁可手写。

## 五、浏览器自动化

### 19. 整页重载会把登录态打掉

- **现象**：每换一次页面就跳回登录，看起来像「平台坏了」。
- **根因**：OneNET 控制台是单页应用，登录态绑在当前会话；用地址栏跳转/刷新等于重新握手，
  握手失败就白屏或跳登录。子域（`open.iot.10086.cn`）还有自己独立的会话。
- **确认**：看跳转 URL 里带 `redirect` 参数，说明是重定向到登录，不是渲染失败。
- **修法**：只在已登录的标签页里点链接，不碰地址栏、不刷新。
- **教训**：自动化操作网页时，「导航」和「点击」是两种风险等级完全不同的动作。

### 20. 同一账号两个会话会互相挤下线

- **现象**：我这边刚点两下就掉登录，用户那边一直正常。
- **根因**：同一账号在同一浏览器里被两个上下文同时使用，令牌刷新会互相覆盖。
- **修法**：要么借用用户已登录的标签页，要么等用户不用时再操作。
- **教训**：多人/多代理同时操作同一后台，先约定谁持有会话。

### 21. 桌面操控切窗口会干扰用户

- **现象**：屏幕上画面乱闪，用户以为在疯狂刷新。
- **根因**：为了把目标窗口调到前台，反复 `Alt+Tab`。
- **修法**：只在目标窗口已在前台时点击；需要调前台时先跟用户说一声。
- **教训**：操作别人的电脑，「不干扰」和「做对」同等重要。

## 六、流程

### 22. 写 NVS 的 `save` 被复位打断

- **现象**：串口依次发完 `cfg ...` 和 `save`，重启后配置是空的。
- **根因**：发完命令立刻用 RTS 复位，最后一条 `save` 还没被解析就重启了。
- **确认**：复位前先读回 `show`，确认字段已生效。
- **修法**：命令之间留足间隔，用 `save` 的确认输出当同步点，再发 `reboot`。
- **教训**：串口是异步的，「发出去」不等于「处理了」。

---


### 23. 服务器对所有鉴权失败都回 CONNACK 5

- **现象**：规范写「4=用户名或密码错误，5=未授权」，但同学们无论密码错还是组号没登记，一律看到 5，
  于是全被引到"账号没开通"这条死路上。
- **根因**：这个 broker 在认证失败时统一返回 5，不区分"密码不匹配"和"账号不存在"。
- **确认**：固定同一 clientId，只改密码：正确密码回 0，故意写 `00000000` 回 5。
- **教训**：返回码的含义要以**实测**为准，规范里的表只能当参考；拿同一组参数做对照实验，
  比反复猜快得多。
