# 密码算对了为什么还是连不上 · 诊断报告

> 对象：`124.70.71.221:1883`（智联迷城）。依据《MQTT通信协议规范·学生版 v2.0》第三节与附录。
> 所有结论都来自实测，命令与返回码附在文末，可复现。

---

## 一、先给结论

「密码不对」只是表象。实测下来有三个独立问题，按严重程度排：

| # | 问题 | 影响 | 谁的问题 |
|---|---|---|---|
| 1 | 服务器是**白名单制**，只有账号表里存在且密码匹配的组号才放行 | 没登记的组号，密码算得再对也是 5 | 组号/账号登记 |
| 2 | 服务器对**所有**鉴权失败一律返回 `CONNACK 5` | 分不清「密码错」和「组号没登记」，容易乱试 | 服务器行为 |
| 3 | 同学们的实现普遍有 bug：MAC 多一位、没取余、按十进制打印 | 算出来的根本不是 8 位十六进制 | 代码 |

其中第 2 条最误导人——规范第 3.4 节写「4=用户名或密码错误，5=未授权（账号没开通）」，
但实测**连错密码也返回 5**，于是所有人都被引向"账号没开通"这条死路。

---

## 二、实测证据

### 2.1 对照实验（同一时刻、同一服务器）

| 组号 | 密码来源 | Client ID | 结果 |
|---|---|---|---|
| 240401 | 按规范算出 `00049916` | `esp32-240401` | **0 ACCEPTED** |
| 240401 | 故意填 `00000000` | `esp32-240401` | 5 |
| 24014 | 按规范算出 `00014bd3` | `esp32-24014` | 5 |
| 24017 | 按规范算出 `0001ab33` | `esp32-24017` | 5 |
| 249999 | 按规范算出 `0004be94` | `esp32-249999` | 5 |
| 240402 | 按规范算出 `00049917` | `esp32-240402` | 5 |

三条推论：

1. **算法本身没问题**——240401 用规范算法算出的密码，服务器认。
2. **错密码也返回 5**——第 2 行与第 1 行只差密码，返回码从 0 变 5，而不是 4。
3. **没登记的组号一律 5**——249999/240402 这种凭空造的组号，即使按本板 MAC 正确推导，也被拒。

### 2.2 服务器上有哪些组在跑

```
GET http://124.70.71.221/iot/api/leaderboard
{"list":[{"rank":1,"name":"验证板","device_id":"99002","score":20,"level":2},
         {"rank":2,"name":"验证板","device_id":"240401","score":10,"level":1}]}
```

排行榜只出现过 99002 和 240401 两台。也就是说**目前全服只有这两个账号真正连通过**，
其余组号连一个都没有成功过——不是个别同学算错，是这一批组号都没进账号表。

## 三、同学那份代码具体错在哪

他串口打印的是：

```
MAC=2C:BC:BB:8A:5D:32:11   CLIENT_ID=ZL-M-2CBCBB8A5D3211
PASSWORD=25031460
```

对着规范逐条比，至少三处不对：

### 3.1 MAC 打出来是 7 个字节

`2C:BC:BB:8A:5D:32:11` 去掉冒号是 **14 位**十六进制，而 MAC 只有 6 字节 12 位。
多出来的 `11` 说明码里按 7 个字节循环了，常见写法是

```c
uint8_t mac[6];
esp_read_mac(mac, ESP_MAC_WIFI_STA);
for (int i = 0; i < 7; i++) ...   // ← 越界读，第 7 个数是内存里的垃圾
```

规范附录的 C 版实现是 `for (i = 0; i + 4 <= hex_len; i += 4)`，14 位时只会吃前 12 位，
所以**多这一位不一定改变结果**，但它说明代码对 MAC 长度的假设是错的。

### 3.2 密码 25031460 超出 2^24

`2^24 = 16777216`，而他打印的 `25031460 > 16777216`。
只要做了 `mod 2^24`，结果**不可能**超过这个数。**说明取余这一步根本没生效。**

### 3.3 打成了十进制，不是十六进制

规范要求「转成 8 位十六进制，不足左边补 0」。`25031460` 全是数字，看着像十进制。
正确输出应该形如 `0001ab33`。

### 3.4 Client ID 不符合规范

规范要求 `esp32-<组号>`，他用的是 `ZL-M-2CBCBB8A5D3211`。
这个格式服务器不认——单独拿正确的密码配这个 Client ID 去连，依然是 5：

```
clientId=ZL-M-2CBCBB8A5D3211  pass=0001ab33  ->  5
```

### 3.5 他那一组的正确密码应该是多少

用他打印的 MAC 前 6 字节（`2C:BC:BB:8A:5D:32`）和组号 24017：

```
H      = 2CBCBB8A5D32
SUM    = 24017 + 2026 = 26043
M1..M3 = 11452, 48010, 23858
TOTAL  = 109363
密码   = 109363 mod 16777216 = 0x0001ab33
```

但拿这个去连，服务器仍然回 5（见 2.1 表），因为 24017 这个组号在服务器上没登记。

---

## 四、所以正确的处理顺序

1. **先修代码**（否则永远不知道是哪种原因）：
   - MAC 只取 6 字节 12 位，先 `WiFi.mode(WIFI_STA)` 再读；
   - `TOTAL % (1 << 24)`；
   - `printf("%08lx")` 或 Arduino 的 `snprintf(out, 9, "%08lx", total % (1UL << 24))`；
   - Client ID 改成 `esp32-<组号>`。
2. **再确认组号已登记**：拿修好后算出的密码去 MQTT.fx 连一次。
   - 回 0 → 账号没问题，直接烧进代码；
   - 回 5 → 密码或登记有问题，把「组号 + MAC + 算出的密码」发给老师，
     请老师在 `/admin` 后台核对该组的密码（那个接口要登录，学生侧看不到）。
3. **不要用返回码区分原因**——这个服务器只会给 5，别在 4 上浪费时间。

## 五、附：自查工具

仓库里 `software/tools/gen_pass.py`：

```bash
python gen_pass.py 24001 A0:B1:C2:D3:E4:F5          # 应输出 0002ae24（规范算例）
python gen_pass.py --selftest                        # 内置算例自检
python gen_pass.py 24017 2C:BC:BB:8A:5D:32 --probe   # 算完顺手实测连服务器
```

它会主动拦掉两类常见错误：MAC 不是 12 位、组号不是十进制。
`--probe` 直接给 CONNACK 返回码，省去开 MQTT.fx 的时间。
